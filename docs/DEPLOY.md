# Deploy

Backend on **Render** (free plan), frontend on **Vercel**, both from this GitHub repo. Every
push to `main` redeploys both.

The two sites must know each other's address: the frontend calls the backend
(`VITE_API_BASE_URL`), and the backend only accepts browsers coming from the frontend
(`CORS_ALLOWED_ORIGINS`). So: deploy the backend first, then the frontend, then give the
backend the frontend's address.

## 1. Backend (Render)

The service is described in [`render.yaml`](../render.yaml) (root directory, build and start
commands, health check, variables).

1. **New → Blueprint** → pick this repo. Render reads `render.yaml` and asks for the
   variables marked `sync: false`:

   | Name | Value |
   |---|---|
   | `HERE_API_KEY` | your HERE key |
   | `ALLOWED_HOSTS` | the Render address without `https://`, e.g. `spotter-backend.onrender.com`. Render shows it after the first deploy; if you don't know it yet, enter `spotter-backend.onrender.com` and correct it later. |
   | `CORS_ALLOWED_ORIGINS` | leave a placeholder for now (e.g. `https://example.com`); set it in step 3 |

   `DJANGO_SECRET_KEY` is generated by Render and `DEBUG` is `false`.
2. Check: `https://<render-address>/api/health` shows `{"status":"ok"}`.

**Without Blueprints:** New → Web Service → this repo, then copy `rootDir`, `buildCommand`,
`startCommand` and `healthCheckPath` from `render.yaml` into the form, and add the variables
above plus `DEBUG=false` and a `DJANGO_SECRET_KEY`:

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(50))"
```

## 2. Frontend (Vercel)

1. **Add New → Project** → import this repo.
2. **Root Directory:** `frontend`. Vercel detects Vite (build `npm run build`, output `dist`).
3. **Environment Variable:** `VITE_API_BASE_URL` = `https://<render-address>` (no trailing
   slash). Vite builds this into the page, so after changing it, **redeploy**.
4. Deploy and note the address, e.g. `https://spotter-routing.vercel.app`.

## 3. Connect them

In Render → the service → Environment, set `CORS_ALLOWED_ORIGINS` = the Vercel address
exactly (with `https://`, no trailing slash) and save; Render redeploys. Then plan a trip on
the Vercel site.

Vercel *preview* deployments get other addresses, so their API calls are blocked by CORS.
Only the production address is allowed, on purpose.

## The free plan sleeps

Render's free services stop after ~15 minutes without requests. The next request wakes it
and waits about 30–60 s, then everything is fast again. The first plan after waking also
starts with an empty weather cache. Before a demo, open `https://<render-address>/api/health`
once and wait for `{"status":"ok"}`.

## If something fails

| Symptom | Likely cause |
|---|---|
| Build fails: Python version doesn't satisfy `>=3.12` | Render's Python is older. Add the variable `PYTHON_VERSION` with a 3.12+ version Render supports (see Render's "Python version" docs) and redeploy. |
| Deploy fails at start, log names a variable | `HERE_API_KEY` (or another required variable) is missing |
| Site says "Could not reach the server" | `VITE_API_BASE_URL` wrong or not redeployed; or CORS: the browser console shows a CORS error, fix `CORS_ALLOWED_ORIGINS` |
| Every call: "The server answered with status 400" | `ALLOWED_HOSTS` doesn't match the Render address |
| First plan takes about a minute | The free service was asleep (see above) |
| "Weather service's request limit was reached" | Open-Meteo's free per-IP limit; Render's outgoing IP is shared |

## Why these settings

- **One gunicorn worker, 8 threads:** the weather cache lives in memory, so one process
  means every request shares it. Threads serve requests that wait on HERE and Open-Meteo.
- **gzip on:** a plan response is ~565 KB of JSON (route lines), ~153 KB compressed.
